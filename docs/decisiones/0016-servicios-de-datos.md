# ADR-0016 — Servicios de datos (bases de datos y extras)

- **Estado:** aceptada (F9.1, F9.2 y F9.4 implementadas)
- **Fecha:** 2026-10-16

## Contexto

La Fase 9 añade MySQL, MariaDB, PostgreSQL y otros servicios que, a diferencia de Nginx y PHP, guardan **datos del usuario**. Un fallo aquí no es un reinicio: es una base corrupta. ADR-0006 (sin secretos en la config), ADR-0007 (MySQL y MariaDB excluyentes) y ADR-0008 (home privada) ya fijan parte del marco.

## Decisión

1. **Cada base de datos es un servicio propio** (`DbService` dentro de un `DbStack`), no parte de la pila web. `crisol start` arranca la pila web y las bases con `enabled = true`; `crisol start mysql` / `stop mysql` / `restart mysql` arrancan una sola. **Una que no puede arrancar** (puerto ocupado por Herd o Devaron, instalación ausente, inicialización fallida) queda `failed` en `status` con su razón y es un **aviso** en el `start` general: no impide que la pila web ni las demás funcionen. Si no hay Nginx pero hay una base habilitada, `start` arranca las bases y avisa.
2. **Exclusión por puerto, no por nombre.** MySQL y MariaDB comparten 3306 por defecto, así que arrancar la segunda con la primera activa se rechaza (`Conflict`, quién tiene el puerto y `crisol stop <la otra>`). Si el usuario les dio puertos distintos, pueden convivir: no hay colisión que evitar. Una colisión con un programa ajeno nunca se resuelve matándolo (ADR-0007): la falla nombra al dueño del puerto.
3. **Datos separados por serie** (F9.5): `data/<servicio>/<mayor.menor>/` (`8.4`, `11.8`, `10.11`). Dos versiones de series distintas no comparten ni corrompen datos; subir de serie es una carpeta nueva, nunca una actualización en el sitio. La configuración generada es `etc/<servicio>/<serie>/my.ini`; lo del usuario va en `etc/<servicio>/overrides/*.ini` (incluido con `!includedir`, nunca tocado).
4. **Inicialización una sola vez y atómica.** Si no existe `data/<servicio>/<serie>/`, se inicializa en `…/<serie>.init/` (MySQL: `mysqld --initialize-insecure`; MariaDB: `mariadb-install-db`) y **solo si termina con éxito** se renombra a su sitio. Una inicialización fallida, cancelada o interrumpida no deja una carpeta de datos a medias que parezca buena: la carpeta `.init` sobrante es nuestra y se borra antes de reintentar. La inicialización tiene tope de 180 s.
5. **Root sin contraseña y solo desde este equipo** (ADR-0006): `bind-address = 127.0.0.1`; ningún secreto en `crisol.toml` ni en `my.ini`. **Pendiente:** poner una contraseña a root desde configuración (referencia `{ env = … }` o credencial del sistema, ADR-0006) no está implementado; requiere arrancar el servidor y ejecutar un `ALTER USER`, y se hará con el comando de gestión de usuarios.
6. **Parada ordenada:** `mysqladmin shutdown` por TCP con 30 s de gracia antes de matar el grupo (matar una base obliga a recuperar el log en el siguiente arranque). El camino de la parada queda en el log (`StopPath`).
7. **Salud por puerto**; el arranque tiene hasta 90 s (la recuperación tras un cierre sucio puede tardar).
8. **MySQL sin `skip-name-resolve`**: `--initialize-insecure` solo crea `root@localhost` y una conexión desde 127.0.0.1 es esa cuenta únicamente si el servidor asocia la dirección de loopback a `localhost` (hallazgo con el MySQL 8.4 real). MariaDB sí lo usa (crea `root@127.0.0.1` y `root@::1`). MySQL desactiva el protocolo X (`mysqlx = OFF`) para no abrir el 33060 sin necesidad.

9. **PostgreSQL (F9.2)** sigue el mismo patrón con sus herramientas: `initdb -U postgres -A trust -E UTF8` en la carpeta `.init`; `postgresql.conf` generado en `etc/postgresql/<mayor>/` (`listen_addresses = '127.0.0.1'`, el puerto de `crisol.toml`, registro a `stderr` hacia `runtime.log`, `include_dir` hacia las configuraciones del usuario) y pasado con `-c config_file=`; el superusuario `postgres` **sin contraseña, por `trust`, solo desde este equipo**. La serie de los datos es solo la versión mayor (`data/postgresql/18/`, `17/`). La salud es `pg_isready` (el puerto se abre antes de que el servidor acepte conexiones) y la parada `pg_ctl stop -m fast`. **Certeza de la fuente:** EDB no publica hash ni firma y sus ejecutables no llevan Authenticode: solo hay integridad de la transferencia (hash idéntico en dos descargas), ver `analisis/fuentes-binarios.md`.
10. **Servicios sencillos (F9.4): MongoDB, Mailpit y Meilisearch.** Mismo `DbService` y `DbStack`, sin inicializador (la carpeta de datos se crea vacía, sin `.init`), sin archivo de configuración nuestro (todo va en la línea de órdenes: `127.0.0.1`, el puerto de `crisol.toml`, los datos en `data/<servicio>/<serie>/`) y listos cuando escuchan todos sus puertos (Mailpit: web y SMTP). **No tienen orden de apagado utilizable**, así que la parada termina el grupo: MongoDB no ofrece `shutdown` fuera de un cliente (`mongosh` no viene en el archivo) y los tres recuperan sus datos desde su propio registro; la prueba real los detiene en 0,2 s y arrancan de nuevo sin problema, pero un cierre limpio de MongoDB mejoraría con un cliente. **Sin telemetría (ADR-0004):** Meilisearch con `--no-analytics`, Mailpit con `--disable-version-check`; MongoDB no envía nada por defecto. Series de los datos: Meilisearch `mayor.menor` (cambia de formato entre menores), MongoDB `mayor.menor`, Mailpit `mayor`. **Redis y Garnet** (alternativas excluyentes en el 6379, ADR-0017) usan el mismo patrón. **Memcached queda fuera** (no hay build oficial para Windows; pregunta al propietario).

## Consecuencias

- `Daemon` conoce a `DbStack`; `status` lista las bases instaladas (paradas) y las arrancadas.
- Pruebas reales a pedido (`crisol-platform/tests/databases.rs`) con los binarios oficiales en los puertos 19306 a 19308, 19432 a 19433, 19017, 19025/19026 y 19700: primer arranque con inicialización (1,7 s MariaDB, 4,5 s MySQL, 6,3 s PostgreSQL), consulta, datos persistentes, parada ordenada (0,25 s, 1,0 s y 0,25 s), segundo arranque sin reinicializar.
- Los servicios siguientes (PostgreSQL, Redis, Mailpit…) reutilizan el patrón: plan, configuración generada, inicialización en `.init`, parada ordenada y estado propio.

## Corrección (2026-10-17, revisión de la Fase 9)

Decidida por el propietario a partir de `claude/revisiones/2026-10-17-opus-fase9.md`. Sustituye a «root sin contraseña» de los puntos 5 y 9.

- **Contraseñas generadas (implementado).** `127.0.0.1` protege de la red, pero no de otras cuentas del equipo: con un superusuario sin contraseña, otra cuenta puede ejecutar código con tu usuario (PostgreSQL `COPY … TO PROGRAM`, MySQL/MariaDB `INTO OUTFILE`, Redis `CONFIG SET dir` + `SAVE`), justo lo que el ADR-0008 cierra en el disco.
  - **Dónde viven:** `secrets/` en la home, creada con `PrivateDirs` y comprobada como `certs/` (`secrets::ensure_dir`; si otra cuenta puede escribir en ella o es de otra cuenta, no se lee ni se escribe nada). Un archivo por servicio y serie (`secrets/mysql-8.4`); se generan con `getrandom` (CSPRNG del sistema), 32 letras y dígitos sin sesgo. Nunca en `crisol.toml`, en el `my.ini`, en la línea de órdenes visible ni en los logs; `Secret` se imprime como `<secret>`, y `ProcessSpec` oculta los valores de las variables de entorno en su `Debug`.
  - **Cómo la recibe cada servicio:**
    - *PostgreSQL:* `initdb -A scram-sha-256 --pwfile=<archivo privado>`, borrado al terminar (o al fallar). `pg_ctl` y `pg_isready` no necesitan contraseña. La prueba real comprueba que **se rechaza a quien no la tiene aunque venga de 127.0.0.1**.
    - *MySQL:* `--initialize-insecure` más `--init-file=<archivo privado>` con `ALTER USER 'root'@'localhost' IDENTIFIED BY …`, borrado al terminar la inicialización.
    - *MariaDB:* `mariadb-install-db` y, en el primer arranque, un `--init-file` privado (`ALTER USER IF EXISTS` para `root@localhost`, `127.0.0.1` y `::1`) que el servidor ejecuta **antes de aceptar conexiones**; se borra en cuanto el servicio está en marcha.
    - *`mysqladmin shutdown`* (MySQL y MariaDB) lee `--defaults-extra-file=<archivo de opciones privado>` con el usuario, el puerto y la contraseña.
    - *Redis:* el *port* de Windows lee un archivo de configuración como primer argumento; todo (incluido `requirepass`) va en `secrets/redis-<serie>.conf` y la línea de órdenes es solo esa ruta. `redis-cli shutdown` recibe la contraseña por `REDISCLI_AUTH` en su entorno.
    - *Garnet:* `--config-import-path` con un JSON privado (`AuthenticationMode: Password`, `Password`).
    - *Meilisearch:* `MEILI_MASTER_KEY` en el entorno del proceso (la clave no está en los argumentos).
    - *MongoDB:* `--auth` y, en el primer arranque con la carpeta de datos vacía, el usuario `root` (rol `root`) se crea por la *localhost exception* con la contraseña generada, por `OP_MSG` y SCRAM-SHA-256 propio (`mongowire`). Mientras no exista, un marcador `secrets/mongodb-<serie>.pending` dice que se debe; si el servidor lo rechaza 5 veces el arranque falla y lo dice. Datos hechos antes de las contraseñas siguen sin `--auth`.
  - **`secure_file_priv`** apunta a `data/<servicio>/<serie>-files/` en MySQL y MariaDB; la prueba real comprueba que `INTO OUTFILE` fuera de esa carpeta se rechaza y dentro funciona.
  - **`crisol db credentials <servicio>`** muestra las líneas para el `.env` (`DB_CONNECTION`, `DB_HOST`, `DB_PORT`, `DB_USERNAME`, `DB_PASSWORD`; `REDIS_PASSWORD`; `MEILISEARCH_KEY`). La respuesta del daemon lleva el protocolo a la versión 2.
  - **Bases ya inicializadas sin contraseña** (las de las pruebas) **no se migran**: siguen funcionando como se hicieron y `crisol db credentials` lo avisa. Para dárselas hay que pararlas, borrar su carpeta `data/<servicio>/<serie>` y arrancarlas (los datos se pierden).

- **Mailpit detrás de Nginx (implementado).** La interfaz y la API se sirven como `mail.<tld>` a través de Nginx (`etc/nginx/sites/_mail.conf`, solo si `[services.mailpit]` está habilitado; un nombre con `_` no puede chocar con un sitio): `proxy_pass` al puerto de Mailpit con `Host: $host` y las cabeceras de WebSocket (la página se actualiza en vivo). El `default_server` de Nginx cierra la conexión (444) para cualquier otro nombre. Además, Mailpit arranca con `--allowed-hosts mail.<tld>` y **él mismo** responde 403 a cualquier otro `Host`: sin esto, una página con *DNS rebinding* podía llegar directo a `127.0.0.1:<puerto>` con su propio nombre. Prueba real a pedido (`mail_behind_nginx.rs`): `mail.test` llega por Nginx; `evil.example`, `127.0.0.1` y otros nombres por Nginx no llegan; directo al puerto de Mailpit con un nombre ajeno da 403. **Límite medido:** Mailpit sigue contestando bajo los nombres de loopback (`127.0.0.1:<puerto>`, `localhost`) aunque no estén en la lista; son peticiones desde este equipo y una página no puede leer la respuesta (su cabecera CORS va vacía). El SMTP sigue en `127.0.0.1` con su puerto. La página es HTTP (no hay certificado para `mail.<tld>`).
- **MongoDB se detiene con su comando `shutdown` nativo (implementado).** `OP_MSG` sobre TCP, sin `mongosh` ni dependencias nuevas (`sha2`, `hmac`, `base64` y `getrandom` ya estaban), con la credencial generada (sin ella, solo para datos antiguos sin contraseña). Va como `StopHook` del servicio: se pide en un hilo aparte y el periodo de gracia (30 s) espera a que el grupo se vaya; matarlo queda como último recurso. Prueba real: parada en ~0,2 s con el log de `mongod` mostrando el apagado, `listDatabases` sin sesión rechazado con el código 13 y una contraseña equivocada que no detiene nada.
- **Memcached (implementado)** con el build de terceros `jefyt/memcached-windows` (memcached 1.6.8 de 2020, compilado en 2026), marcado `end_of_life` y con certeza menor; sin contraseña (sin SASL), y `doctor` lo dice. Detalle en la corrección del ADR-0017.
- **Avisos de la revisión (hallazgos 4 a 6, implementados).**
  - **Configuración de MySQL/MariaDB:** además de `secure_file_priv`, `local_infile = OFF` (probado con los tres servidores reales).
  - **Cambio de puerto con la base en marcha:** el daemon compara cada 2 s el puerto de lo que corre con `crisol.toml` y avisa **una vez**: «`mysql` is still on port 3306; `crisol restart mysql` to use 3307». No reinicia por su cuenta: cortaría las conexiones de las aplicaciones.
  - **Serie nueva junto a otra con datos:** al arrancar una serie que empieza vacía mientras otra del mismo servicio tiene datos, `crisol start` avisa dónde están (`data/mariadb/11.8`) y que no se migra nada, con la herramienta de exportación (`mysqldump`, `pg_dump`, `mongodump`). `crisol doctor` lista los servicios con datos en más de una serie (`data series`).
- **`crisol enable|disable <servicio>` (implementado)** edita solo `enabled` en `crisol.toml` con `TomlEditor` (comentarios, orden y demás claves quedan; si ya estaba así no escribe nada). Al habilitar avisa si el servicio es alternativa de otro habilitado (MySQL/MariaDB, Redis/Garnet) o si comparte puerto con uno habilitado, y aun así escribe: el archivo es del usuario y `doctor` y `start` dicen lo mismo. Deshabilitar no detiene lo que corre: lo dice y señala `crisol stop <servicio>`. Solo vale para los servicios de datos.

## `crisol db reset-password <servicio>` (2026-10-17, V3 de la verificación manual de la Fase 9)

Cambia la contraseña generada de un servicio **con el servicio en marcha y sin perder datos**, y actualiza `secrets/`. Necesita el daemon (pregunta al servidor con la contraseña vieja). Cómo, por servicio:

| Servicio | Cómo | ¿En marcha? |
|---|---|---|
| MySQL, MariaDB | `ALTER USER` por el cliente `mysql` (el SQL entra por su entrada estándar; el archivo de opciones privado lleva la contraseña vieja) | sí |
| PostgreSQL | `ALTER ROLE postgres PASSWORD` por `psql` (la vieja en `PGPASSWORD`, el SQL por la entrada estándar) | sí |
| Redis | `CONFIG SET requirepass` por una conexión normal; el comando de parada (`redis-cli`) se rehace con la nueva | sí |
| MongoDB | `updateUser` por el protocolo de red; el gancho de parada lee la contraseña del archivo en el momento de usarla | sí |
| Garnet, Meilisearch | no es posible: leen la contraseña solo al arrancar | parado: se escribe la nueva para el siguiente arranque; en marcha: se niega y dice cómo (`crisol stop`, repetir, `crisol start`) |
| Mailpit, Memcached | no tienen contraseña | – |

Orden seguro: la contraseña nueva espera en `secrets/<servicio>-<serie>.next` mientras se le pide al servidor; si lo rechaza, se borra y todo queda como estaba; si lo acepta, reemplaza al archivo y se rehacen los archivos de ejecución (opciones de `mysqladmin`, configuración de Redis). Una base hecha antes de las contraseñas: MySQL y MariaDB aceptan recibir una (entran sin contraseña); PostgreSQL y MongoDB (sin `--auth` o con `trust`) piden reinicializar. Después hay que actualizar el `.env` de los proyectos (`crisol db credentials`). El protocolo sube a la versión 3 (24 operaciones).

## MongoDB: el primer usuario se crea en un puerto efímero (2026-10-17, Y1)

Con la carpeta de datos vacía, MongoDB deja que el primer programa que pregunte cree el primer usuario (*localhost exception*). Antes eso pasaba en el puerto real; cualquier cuenta del equipo podía ganar la carrera. Ahora el primer arranque (marcado por `secrets/mongodb-<serie>.pending`) se hace en un puerto que el sistema asigna al azar (`MongoAdmin::free_port`, un `bind` al puerto 0), con `--auth`, **solo** para crear el usuario `root` con la contraseña generada; después se le pide que salga (`shutdown` con esa credencial) y se arranca el servidor real en el puerto de `crisol.toml`, que ya encuentra el usuario. Mientras tanto el servicio figura como `starting`. Si el usuario no se puede crear tras 5 intentos (o el servidor temporal no arranca), se **borra la carpeta de datos** (solo tiene lo que MongoDB acaba de crear), el marcador y la contraseña, y el siguiente `start` empieza de cero; el usuario ya no tiene que borrar nada. Una parada durante ese primer arranque mata el servidor temporal y deja el marcador: el siguiente `start` repite el paso.
